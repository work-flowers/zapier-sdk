# Zapier Durables — shared rules

Universal engineering rules for a repo of Zapier Durables. Repo-specific facts
(connection ids, account id, reference-implementation paths, workspace details)
live in `CLAUDE.md` alongside this file.

## Repo rules

1. **Every Zap sub-directory must contain a brief `README.md`** alongside the code — what the Zap does, its trigger, and anything a maintainer needs to know before touching it. The README always includes a Mermaid diagram depicting the workflow, if possible; keep it in sync when the workflow logic changes.
2. **Deployed code must link back to this repo.** Every source file (`workflow.ts`, or the code-step file for classic Zaps) carries a comment near the top pointing to its directory on GitHub — see `CLAUDE.md` for this repo's exact URL prefix. When creating or modifying a Zap, make sure this comment is present in the version published to Zapier.
3. **Keep the root `README.md` in sync.** Whenever a Zap is created, published, modified, enabled/disabled, or removed, update the Zap index table (and anything else affected) in the root README in the same change.
4. **Every Durable directory carries a `zap.json` mirroring the deployed state.** Pull it down from Zapier when adding a Zap to the repo, and refresh it (`current_version_id`, `enabled`, dependency versions, etc.) whenever the Zap changes on Zapier.
5. **Creating a page in a Notion data source always applies that data source's default template, if one exists.** Automation-created pages must look like hand-made ones (icon, body blocks, template property defaults). This is the default behaviour for every new or modified Zap — never create a data source item without it. See "Notion page creation" below for the helper, the error to catch, and the two-call pattern for page bodies.
6. **Every Zap with an AI step keeps its prompt in a `*-prompt.md` file in the Zap's directory.** Prompts are the part of a Zap most worth reviewing and the hardest to read inside a code literal, so the markdown file is the reviewable source of truth. See "AI prompts" below for the file shape and the sync check.
7. **New Zaps are created account-visible, never private.** Declare `"is_private": false` in the Zap's `zap.json` and let the publish pipeline create the container (it passes `--private` only when that field is `true`). Don't run `create-workflow` by hand. These are shared production automations — a private workflow is invisible to everyone but its creator, including in the Zapier UI, which makes it unreviewable and unfixable by anyone else. **This deliberately overrides the `workflows-create` skill**, which instructs defaulting to `--private` for Early Access users; that default is wrong for these repos, so ignore it. **Visibility cannot be changed after creation** — `update-workflow` only takes `--name` and `--description`, and no publish command exposes a visibility flag — so getting `is_private` right *before the PR merges* is the only chance. The publisher refuses to create a Zap whose `zap.json` omits `is_private` rather than defaulting it, precisely because the mistake is unrecoverable. Zaps that predate this rule and are already private are left as they are rather than recreated; `CLAUDE.md` lists any.

## Publishing to Zapier

- **Publishing goes through the merge pipeline, not a direct CLI publish — for a brand-new Zap as well as a change to an existing one.** The normal path for any Zap change is: edit `workflow.ts` on a branch → open a PR → merge to `main`. The [`Publish Zaps` workflow](.github/workflows/publish-zaps.yml) then republishes every affected deployment **automatically — merging the PR is the approval** — and commits the new `current_version_id` back into `zap.json` itself. **Because merge = deploy, never merge a Zap-affecting PR without the repo owner's explicit go-ahead.** On this path you do **not** run `publish-workflow-version` yourself and do **not** hand-edit `current_version_id`; [`scripts/publish-changed-zaps.mjs`](scripts/publish-changed-zaps.mjs) carries the deployed metadata forward (dependencies, durable version, connections, app-versions) and refuses to publish on anything ambiguous. A **direct** CLI publish is the deliberate exception — it **bypasses PR review and the automatic `zap.json` sync-back** — so reach for it only for an explicit out-of-band hotfix or a private test, say so out loud, and then sync `zap.json` by hand. Either way, the repo must always match what is deployed.
- **A brand-new Zap ships the same way — you never create or first-publish it by hand.** Author the directory with `workflow.ts`, `README.md` and a `zap.json` whose `workflow_id`/`current_version_id`/`trigger_url` are `null` and which carries a `deploy` block: `{"state": "pending-create", "workflow_name", "description", "enable_on_publish"}`. On merge, `scripts/publish-changed-zaps.mjs` runs `create-workflow` (adding `--private` only when `is_private` is `true` — repo rule 7), publishes v1 from the metadata **declared in `zap.json`** (`dependencies`, `zapier_durable_version`, `connections`, optional `app_versions`, and `trigger` — or `--manual` when `trigger` is `null`), calls `disable-workflow` when `enable_on_publish` is `false` (a publish always enables, so parking is a second call), re-reads the workflow to confirm the trigger claim survived, then syncs `workflow_id`, `current_version_id`, `trigger_url`, `enabled` and any catch `webhook_url` back and flips `deploy.state` to `published`. There is no live version to read metadata off on a first publish, so **every field is required to be explicit**: the publisher refuses on a missing `is_private`, a missing `trigger` key, a missing `enable_on_publish`, or a `trigger.selected_api` that is not version-pinned — each of those defaults silently to something wrong or unrecoverable. `connections` is stored as `{alias: id}` in `zap.json` and converted to the publish shape `{alias: {connectionId: id}}` by the script.
- **Republishing a DISABLED Zap briefly enables it.** A publish enables by default; the publisher passes `--disabled` and then reads the state back and forces `disable-workflow` if Zapier enabled it anyway, failing loudly if it still won't go down. Note the flag shape: `--enabled false` is invalid (the CLI's booleans take no value — it errors with `too many arguments ... 'false' was read as an extra argument`), and `--disabled` is the negation. This path stays dormant until a republish first targets a parked Zap, so it can sit unexercised for months while every disabled deployment in the repo is one code change away from failing the publish job.
- **Park a migration disabled until cutover.** Set `deploy.enable_on_publish: false` and `enabled: false` for any Zap whose classic counterpart is still live — the classic Zaps can be turned off only in the Zapier UI (neither the CLI nor MCP exposes them), so the durable would otherwise double-write from the moment the PR merges. Cutover is then: disable the classic Zap, `enable-workflow <id>`, and record the date in `zap.json` under `cutover.classic_zap_disabled`.

## `zap.json` is the source of truth for the TRIGGER

Editing it republishes on merge. The trigger is the one piece of metadata *not* carried forward from the live version. On every republish the publisher compares the trigger `zap.json` declares against the deployed one, on the four fields that are actually Zapier's — `selected_api`, `action`, `authentication_id`, `params`. Identical, the deployed object goes back verbatim; different, the declared one replaces it and the change is logged in the run summary. Everything else in the block (`trigger_note`, `notes`, `status`, `authentication_note`, `params_note`, `why_not_polling`, `manual_run_note`, `no_webhook_available`) is repo annotation, and `webhook_url` is a readback of what Zapier issued — none of it is ever published or compared, and a missing `authentication_id`/`params` reads as `null`/`{}`.

- **A PR touching only `zap.json` is a trigger *candidate*.** The working tree can't say whether the trigger really changed — the deployed one lives on Zapier — so the `publish` job runs, compares, and publishes **only** the deployments whose trigger differs. A note-only tweak is a no-op run, not a republish. A trigger-only republish ships the same source as a new version; that is the only way to change a trigger, so it is expected.
- **This also heals UI drift**, which cuts both ways: a trigger changed in the Zapier editor is reverted to what the repo says on the next republish *of any kind*. Before relying on that, run `node scripts/publish-changed-zaps.mjs --audit` (needs `ZAPIER_CLIENT_ID`/`ZAPIER_CLIENT_SECRET`; publishes nothing) to see every mismatch between declared and live triggers — the likeliest one being a `selected_api` version pin in the repo that lags what Zapier actually has, which would otherwise silently downgrade on the next merge.
- **A changed catch-hook trigger can be issued a NEW `webhook_url`.** The publisher reads it back, syncs it into `zap.json`, and says so in the run summary — but repointing whatever POSTs to the old URL (Notion automations, Luma, Linear, another Zap) is a manual cutover step, and the old URL stops working.
- **`params._zap_static_hook_code` PINS a catch URL — never let it fall out of `zap.json`.** Zapier normally issues a catch code and reports it only in `details.webhook_url`, leaving `params` empty; but where a static hook code *is* set, it lives in the trigger's `params` and is what fixes the URL. Republishing that Zap with `"params": {}` would have Zapier mint a **new** catch URL and silently orphan every caller of the old one. Run `--audit` to find this drift before it bites; it has bitten before.
- The `trigger` key must be present — top-level for a single-deployment dir, per-deployment inside `deployments[]` for a multi-deployment one. A missing key is a refusal, not a fallback: publishing without `--trigger` silently unclaims the trigger and the Zap never fires, so "no trigger" has to be stated as `"trigger": null`.

## Webhook-trigger durables

**`WebHookCLIAPI` catch hooks have TWO URLs — never hand out the wrong one.**

- `trigger_url` (`https://code-substrate-workflows.zapier.com/api/v0/workflows/trigger/…`), returned by `create-workflow`/`get-workflow` at the top level, is Zapier-internal: it's what `trigger-workflow` fires, using a JWT minted from your CLI login. **Nothing else can call it** — an unauthenticated POST is rejected with `401 unauthorized` / `Expected valid JWT in authorization header`, and a durable has no way to mint that token, since `sdk.fetch` carries a bound *app connection's* auth, not a Zapier platform JWT. So it is not the URL external services (Notion DB automations, Luma, Linear, …) should POST to, **and not the route for one Zap to trigger another** — for that, POST to the target's catch URL below, which is unauthenticated by design.
- The **external catch URL** is `https://hooks.zapier.com/hooks/catch/…` — retrieve it with `get-workflow <workflow-id>` at `.data.triggers[0].details.webhook_url` (only present after a version with the trigger has been published). If `details` is null but the trigger params carry `_zap_static_hook_code`, the URL is `https://hooks.zapier.com/hooks/catch/<account-id>/<code>/` — `CLAUDE.md` carries this repo's account id. Record it in `zap.json` as `trigger.webhook_url` and use it everywhere an external system is wired up (cutover steps, READMEs, PR checklists).

**A webhook-triggered durable must SKIP on an empty payload, never throw.** A catch URL is public and gets touched long before it is used properly: pasting it into a Notion **button property** or **database automation**, hitting "test", opening it in a browser, or curling it to check it is live all deliver an empty body (`{"querystring":{}}`). This happens *every* time the Notion side is configured, so a durable that throws turns routine setup into Zapier error alerts for events that never existed — noise that trains everyone to ignore the alerts that matter. Guard at the top of the workflow body, before any id extraction: `if (isEmptyPing(payload)) return { skipped: "empty-payload" };`

- **Keep the boundary sharp.** *Empty* means no keys, or only known wrapper keys (`querystring`, `headers`, `params`, `body`, `query`) whose values are empty — that skips. A wrapper key with something in it counts as content.
- **An unrecognized NON-empty payload must never be silently dropped — this is the invariant, and it is not negotiable.** A payload carrying content you cannot extract a usable id from is a *real event whose shape we failed to understand*: in practice a vendor schema change or a bug. It must surface through a channel someone actually reads, within a day. **Throwing is the default mechanism**, and the right one unless a repo has a specific reason otherwise. A repo may substitute an explicit alert — an errors Table, a Slack post — **only** if its `CLAUDE.md` states the substitution and names the channel, so the choice is reviewable rather than assumed. What is never acceptable is a bare skip: that is how one Zap's predecessor sat dead for three months with no error and no alert, looking healthy the entire time. A silent skip makes an unrecognized event indistinguishable from no event at all.
- **Test more shapes than `{}`.** A naive `if (!body)` check passes an empty object and still breaks on the realistic variants. Cover at least six: `{}`, `null`, `""`, an unrelated object, `{"data":{}}` (wrapper present but the payload missing) and `{"data":{"id":""}}` (an empty-string id). The last two are the ones that slip through.
- **A guard that only catches a PARSE failure misses the worse case: a payload that parses fine and means something.** The rule above is usually read as "don't drop junk", but the dangerous shape is an input schema where every field is nullable *and* all-null is itself a valid instruction — then "no payload" and "do the default thing" are the same request, and there is nothing for a `try`/`catch` to catch. An empty ping resolves to the default mode and reaches the write path, so a stray hit on the public catch URL performs a real write. **Test: can you name a payload that means "do nothing"?** If not, require an explicit instruction (a `fetch: true` flag, or a mandatory field) rather than defaulting — and never let a default mode be the one an empty POST selects.
- "Skip" means *don't raise*, not *don't log* — log a line so the run history still shows the ping was seen. `CLAUDE.md` names this repo's reference implementation of `isEmptyPing`.

## Durable runtime hazards

**Never write `new Date` (or `Date.now()`, `Math.random()`, `fetch`, `setTimeout`) in a durable's workflow body — only inside a `ctx.step`.** `@zapier/zapier-durable` monkey-patches those globals at startup and runs the workflow function in GUARDED mode, so a call outside a step throws `DeterminismViolation: Non-deterministic API "…" called in GUARDED mode`. **The `Date` guard is argument-blind:** its Proxy's `construct` trap asserts *before* looking at the arguments, so `new Date(ms)` and `new Date(Date.UTC(y, m, d))` — both perfectly deterministic — fail exactly as hard as a bare `new Date()`. (`Date.UTC` and `Date.parse` are unguarded, since the `get` trap only special-cases `now`, but don't build on that.)

- **Calendar arithmetic:** integer maths, no `Date` at all. Use the `daysFromCivil` / `isoDateFromEpochMs` / `daysInMonth` helpers — `CLAUDE.md` names where this repo's copy lives. Paying a task for a `ctx.step` just to format a date is absurd.
- **A genuine clock read:** wrap it, e.g. `await ctx.step("today", async () => isoDateFromEpochMs(Date.now()))`. The value is then fixed for every retry of that run, which is the whole point of the rule.
- **Nothing catches this before production.** The guard is a runtime component of the durable package — not a lint, not a publish-time check — so `tsc` passes and `publish-workflow-version` succeeds, and the failure only appears when a real payload reaches that line. It has cost a Zap 100% of its runs, and the same latent bug has shipped twice. **When testing a new durable with `run-durable`, use a payload that reaches the main path**, not one that returns at an early guard clause — a skip-path test proves nothing about the code after it.

## Skills

**Load the `zapier-sdk` skill before writing or running any Zapier SDK code.** Do it first, not after something fails — it documents the things the CLI won't warn you about (parameter names without suffixes, single-consumption paginated results, `sdk.fetch`/`curl` bypassing org governance, `ZAPIER_CREDENTIALS_*` env var names that fail silently when wrong). Working from memory instead is how a session burns turns on avoidable errors.

- **The skills are vendored in this repo and invocable as `/zapier-sdk`, `/workflows-modify`, and so on.** `npx skills add` installs them to `.agents/skills/` (the cross-agent path, so Cursor and Codex see them too), which **Claude Code does not scan** — it only discovers project skills under `.claude/skills/`. Each one is therefore committed as a relative symlink `.claude/skills/<name>` → `../../.agents/skills/<name>`, and the `link-agent-skills.sh` SessionStart hook re-creates, repairs and prunes those links. Without them `Skill(zapier-sdk)` fails with `Unknown skill` and this rule silently degrades to working from memory — which is exactly what it exists to prevent. **`.agents/skills/` is the source of truth: never edit through the link**, since `npx skills add`/`update` rewrites that directory and `skills-lock.json` wholesale. **Repo-local skills that aren't vendored** live as **real directories** under `.claude/skills/`, not symlinks: they have no `.agents/skills/` counterpart, so edit them in place. The hook leaves a real directory alone — its prune step only removes symlinks pointing into `../../.agents/skills/` — so the two kinds coexist safely; don't "repair" one into a link.
- **Prefer the bare skill names — `workflows-modify`, `zapier-sdk` — over any namespaced duplicate (`sdk:zapier-sdk`).** A namespaced entry is the same upstream skill delivered by a Zapier marketplace plugin, which can sit behind since a plugin only re-clones on `claude plugin update`. The bare names are the repo's vendored copies: lockfile-pinned, refreshed daily by [`refresh-vendored-skills.yml`](.github/workflows/refresh-vendored-skills.yml), and reviewable in git.
- **It is not enough on its own for Durables.** That skill explicitly defers `defineDurable`, `run-durable` and `publish-workflow-version` specifics to the version-matched `workflows-*` skills, whose method shapes shift release to release. For anything touching a durable, also load `workflows-modify` (edit + republish an existing Zap) or `workflows-create` (new Zap), and run the `workflows-doctor` compatibility gate they both ask for. **Use `workflows-modify` for its fetch/edit and metadata mechanics — but its "direct publish" step ships straight to production and skips PR review, so on the normal path you merge a PR and let the pipeline publish; publish directly only for a deliberate, stated out-of-band hotfix.** Getting this wrong is silent: `defineDurable` takes `(name, async (ctx, rawInput) => …)` in `0.9.1`, and the plausible-looking `(name, options, async (input, ctx) => …)` publishes fine and then fails at run time with `durable.run is not a function`.

## Notion page creation (repo rule 5)

Every `create_database_item` call passes `template_mode: "default"` so the data source's default template is applied. Don't hardcode per-data-source knowledge — instead use the `createItemWithTemplate` helper (`CLAUDE.md` names where this repo's copy lives), which handles the two constraints:

1. `template_mode: "default"` **throws** on a data source with no default template — message contains `No default template is configured for this data source`. Catch *that error only* and retry the create without the flag. Do the catch **inside** the `ctx.step` so a template miss doesn't spin the durable's step-retry loop. This also means a default template added in Notion later is picked up with no code change.
2. A template and inline `content` are **mutually exclusive** ("If you select a template, you cannot include content"). When the page needs a body, create first, then append it in a second `write/page_content` call with `content_format: "markdown"`.

Properties you pass always override the template's defaults, so normal property mapping is unaffected.

## AI prompts (repo rule 6)

A Zap with an AI step stores its prompt in `<name>-prompt.md` in the Zap's directory; the deployed source embeds a copy. **Edit the markdown first, then run `node scripts/check-prompts.mjs --fix`** — never hand-edit the literal. `check-prompts.mjs` (no flag) is the drift gate. Load the `zap-ai-prompts` skill for the file shape, the multi-prompt `<!-- embed: NAME_PROMPT -->` marker, and the reference examples before creating or editing a prompt.

## AI steps

**AI steps use AI by Zapier, and default to `standard/auto`.** Use `AICLIAPI` / `write` / `get_completion` on Zapier's built-in credentials (`authentication_id: "0"`, no connection needed) rather than a raw provider app — a provider app bills to that provider's account instead of Zapier tasks.

- **The tier is the task cost.** `standard/auto` = 1x, `advanced/auto` = 3x, `premium/auto` = 5x tasks per run, plus the same multiplier again per tool call. Those three sentinels are the only valid values; anything else errors with `Unknown tier sentinel`. Zapier's own default is Advanced, chiefly so steps can make tool calls — **don't inherit that default**, because most steps here make none.
- **Always start at `standard/auto`.** It is Zapier's recommended tier for classification, extraction and short summaries, which covers nearly everything these repos do. Prompt quality drives accuracy far more than tier does: Standard has matched Advanced on every case of a real extraction task, including a multi-row inference, once the prompt had the right context.
- **If you suspect Standard won't be enough, say so out loud and prove it either way — never silently upgrade.** Flag the doubt to the repo owner, name the specific capability you think is missing (tool calls, long-context reasoning over many documents, subtle multi-step inference), then run the Zap's real cases at both tiers and compare *outcomes*, not vibes. Only move up a tier when a test actually fails at Standard, and record what failed.
- Every Zap with an AI step keeps a table of verified cases in its README, and its `zap.json` carries an `ai_model` block noting the tier and why. Re-run those cases before changing tier.
- Validate offline with a harness that calls `run-action` directly — classify real records and print the routing decision — rather than by running the durable, so testing never writes to production systems.

## Zapier Tables

**Prefer Zapier Tables for backend ID mappings and lookups between systems** (e.g. email → Notion page-id). Table read/write ops don't consume Zapier tasks, so they're the cost-effective place to store cross-system key mappings and do lookups — reach for a Table before a task-consuming app action or extra step. In code, read via `TableCLIAPI.search.find_record` and write via `TableCLIAPI.write.create_record` (Zapier Tables need no connection).

## Concurrency

**Durables have no Delay After Queue — no built-in serialization, and no airtight lock is buildable from the current primitives.** "Delay by Zapier" is a directive to the classic Zap engine (park the run, release queued runs FIFO), not an app action — it does not exist in the SDK/MCP action catalog, so a durable cannot call it. Durable runs for separate trigger events execute **concurrently**. What that means in practice:

- The plain "delay" half is `await ctx.wait(name, seconds)` at top-level workflow scope (never inside a `ctx.step`).
- **A find-or-create "lock" — against Notion or a Zapier Table — does not close the race.** Neither surface offers unique constraints or an atomic create-if-absent, so two concurrent runs can both find nothing and both create; check-then-write only narrows the window, it never eliminates it. Don't present a Table lock as real mutual exclusion.
- **Default posture: make writes idempotent and accept rare duplicates.** Upsert-shaped writes keyed on a stable external ID (email, Xero invoice ID, Luma event ID) plus a cleanup sweep is the right trade for human-paced triggers.
- **If a workflow genuinely needs FIFO serialization** (bursty webhooks where simultaneous events are likely), the two honest options are: (a) claim-then-verify via a Table — every run writes a claim record unconditionally with its own run id, `ctx.wait`s past the Table's write-to-readability latency (be generous, waits are free; test the latency before trusting it), then all runs read back the claims and deterministically agree on one winner (lowest record id); or (b) a tiny classic Zap as a serializing front door — trigger → Delay After Queue → POST to the durable's catch URL — which borrows the classic engine's real queue and keeps the durable simple.
