Drive invoice → Xero

A purchase invoice lands as a PDF in one Google Drive folder. This workflow reads it, works out whether it has already been paid, and then either staples the PDF to the payment that settled it — or raises a draft bill in Xero for it.

TL;DR

Stop keying invoices into Xero by hand. Like an animal. Everything below hangs off one question — has this been paid yet? — and every answer lands as a draft that a human still reviews.

If no payment matches Raise a draft bill

Treated as outstanding. Three guards run in order before a bill is created, each one there to stop a specific mess that has actually happened.

1 Already billed? Xero is asked whether a bill with this invoice number exists. Deleted and voided ones don’t count — they must not block a legitimate re-create.
2 Which contact? The vendor is resolved against the existing Xero contacts, and the bill is bound to the name already stored there.
3 Do the lines add up? The extracted lines must reconcile to the invoice total. If they don’t, the bill falls back to a single line for the total — a bill that doesn’t equal the invoice is worse than one without itemisation, and the PDF is attached either way.

The matching rule

Why the amount is required, not a tiebreaker

A ±7 day window is wide. It is only safe because the total has to match to the cent. Each of these is a real invoice from the ledger, and each one breaks a looser rule.

A vendor billed three times in one week Anthropic had three transactions inside four days of a single invoice — 104.58, 133.58, 99.00. Only the amount picks the right one.
A subscription at a fixed monthly price SimplePay bills SGD 12 every month, so the amount alone can’t tell July from August. The date window is what does.
One invoice settled by two payments Aspire FT’s 45.90 invoice was paid as 4.92 + 40.98. Requiring the exact total makes this correctly fail to match, rather than attaching the invoice to half of itself.
The same counterparty, spelled two ways Aspire FT Pte. Ltd. and Aspire FT are one vendor. Legal-entity suffixes are stripped before comparison — in code, for free. This is the only job the old workflow’s AI agent was really doing.

Vendor contacts

A bill binds to a contact by name, so the name has to be the stored one

Xero quietly creates a bare new contact when the name on a bill doesn’t match one exactly. That is how the ledger ended up with four duplicate pairs — Aspire FT sitting alongside Aspire FT Pte. Ltd., and the same for three other vendors. So before raising a bill, the workflow resolves the vendor against the real contact list and passes back the name Xero already knows.

Exactly one match Fill its empty fields Bill uses the stored name
Several matches Change nothing Logged for a human to merge
Partial + email agrees Fill its empty fields Bill uses the stored name
No match Create the contact With address, phone, tax number, bank
A partial name match never binds on its own It is safe against bank transactions only because an exact amount, currency and date must agree too. A contact has no such corroboration, and the same rule would happily merge LinkedIn with LinkedIn Ads. The vendor’s email domain has to agree, or it counts as no match.
Xero’s own contact search can’t make this call Its search is an unranked substring match, so olar returns both Olar Software and Polar Software — two unrelated companies. Suffix-stripped comparison keeps them apart; similarity scoring would not.
Only empty fields are ever filled Existing values are re-sent untouched with every update, so a contact holding two addresses keeps both.
Bank details are written once and never overwritten An emailed invoice asking to be paid into a new account is what invoice-redirection fraud looks like, and a contact’s bank account outlives the bill that introduced it. When an invoice disagrees with a stored account, the workflow leaves the record alone and reports the conflict.

Known hazards

Two things have actually bitten this workflow

Both are worth reading before changing anything, because neither announces itself as an error.

Silent dependency

The payments Table can go stale without erroring

The match reads a Zapier Table, not Xero directly, and a separate workflow keeps that Table fed. This one is only as correct as that one is current.

When the feeder’s predecessor was paused, the Table fell about five days behind: 7 of 43 bank payments were missing — all of them the newest ones, which are exactly the ones an incoming invoice needs to match against.

What it looks like: not an error. Duplicate draft bills appearing in Xero and being deleted by hand. A tableStale flag now measures the Table’s own freshness on every run and trips at 14 days behind — but it is a proxy, not proof. If duplicates start appearing, check the feeder’s run history.

Runtime guard

A date read outside a step fails every single run

The durable runtime replaces Date with a guard before any code runs, and it throws before looking at the arguments — so even a perfectly deterministic date construction is rejected as hard as reading the clock.

The first published version failed on every PDF invoice for this reason. Calendar maths here is integer arithmetic; the clock is read in exactly one place, inside a step, so its value is fixed for every retry.

Why it reached production: nothing upstream catches it — not the type-checker, not publishing. And the one end-to-end test used a non-PDF payload, which returns at the first gate, before the line that threw. Test the path that actually runs.
