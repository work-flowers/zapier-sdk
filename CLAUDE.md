# zapier-sdk

Source-of-truth repo for workFlowers Code Zaps in the main work.flowers Zapier workspace. One sub-directory per Zap — mostly Durables, plus one classic Code-step Zap (`email-contact-page-zap`).

## Repo rules

1. **Every Zap sub-directory must contain a brief `README.md`** alongside the code — what the Zap does, its trigger, and anything a maintainer needs to know before touching it. The README always includes a Mermaid diagram depicting the workflow, if possible; keep it in sync when the workflow logic changes.
2. **Deployed code must link back to this repo.** Every source file (`workflow.ts`, or the code-step file for classic Zaps) carries a comment near the top pointing to its directory on GitHub, e.g.:
   `// Source of truth: https://github.com/work-flowers/zapier-sdk/tree/main/<zap-name>`
   When creating or modifying a Zap, make sure this comment is present in the version published to Zapier.
3. **Keep the root `README.md` in sync.** Whenever a Zap is created, published, modified, enabled/disabled, or removed, update the Zap index table (and anything else affected) in the root README in the same change.
4. **Every Durable directory carries a `zap.json` mirroring the deployed state.** Pull it down from Zapier when adding a Zap to the repo, and refresh it (`current_version_id`, `enabled`, dependency versions, etc.) whenever the Zap changes on Zapier.
5. **Creating a page in a Notion data source always applies that data source's default template, if one exists.** Automation-created pages must look like hand-made ones (icon, body blocks, template property defaults). This is the default behaviour for every new or modified Zap — never create a data source item without it. See "Notion page creation" under Working conventions for the helper, the error to catch, and the two-call pattern for page bodies.
6. **Every Zap with an AI step keeps its prompt in a `*-prompt.md` file in the Zap's directory.** Prompts are the part of a Zap most worth reviewing and the hardest to read inside a code literal, so the markdown file is the reviewable source of truth. See "AI prompts" under Working conventions for the file shape and the sync check.
7. **New Zaps are created account-visible, never private.** Run `create-workflow` **without** `--private` (the SDK CLI already defaults to account-visible, so this means not passing the flag). These are shared production automations for the work.flowers workspace — a private workflow is invisible to everyone but its creator, including in the Zapier UI, which makes it unreviewable and unfixable by anyone else. **This deliberately overrides the `workflows-create` skill**, which instructs defaulting to `--private` for Early Access users; that default is wrong for this repo, so ignore it. **Visibility cannot be changed after creation** — `update-workflow` only takes `--name` and `--description`, and no publish command exposes a visibility flag — so getting it right at `create-workflow` time is the only chance. Record it as `is_private` in the Zap's `zap.json`. `email-db-updates` and `merge-duplicate-contacts` are private because they predate this rule; leave them as they are rather than recreating them.

## Working conventions

- Each Durable directory contains `workflow.ts` (the source as published on Zapier), `zap.json` (workflow ID, current version ID, trigger URL, enabled state, runtime/dependency versions), and `README.md`. Classic Code-step Zap directories carry the code-step source and tests instead.
- **Publishing to Zapier goes through the merge pipeline, not a direct CLI publish.** The normal path for any Zap change is: edit `workflow.ts` on a branch → open a PR → merge to `main`. The [`Publish Zaps` workflow](.github/workflows/publish-zaps.yml) then republishes every affected deployment **automatically — merging the PR is the approval** (the former `production`-environment required-reviewer gate was removed 2026-08-18 as redundant) — and commits the new `current_version_id` back into `zap.json` itself. **Because merge = deploy, never merge a Zap-affecting PR without Dennis's explicit go-ahead.** On this path you do **not** run `publish-workflow-version` yourself and do **not** hand-edit `current_version_id`; [`scripts/publish-changed-zaps.mjs`](scripts/publish-changed-zaps.mjs) carries the deployed metadata forward (dependencies, durable version, connections, app-versions, trigger/manual start mode) and refuses to publish on anything ambiguous. A **direct** CLI publish is the deliberate exception — it **bypasses PR review and the automatic `zap.json` sync-back** — so reach for it only for an explicit out-of-band hotfix or a private test, say so out loud, and then sync `zap.json` by hand. Either way, the repo must always match what is deployed.
- **Webhook-trigger durables (`WebHookCLIAPI` catch hooks) have TWO URLs — never hand out the wrong one.**
  - `trigger_url` (`https://code-substrate-workflows.zapier.com/api/v0/workflows/trigger/…`), returned by `create-workflow`/`get-workflow` at the top level, is Zapier-internal: it's what `trigger-workflow` fires, using a JWT minted from your CLI login. **Nothing else can call it** — an unauthenticated POST is rejected with `401 unauthorized` / `Expected valid JWT in authorization header` (re-verified 2026-08-11 against a disabled Zap's URL), and a durable has no way to mint that token, since `sdk.fetch` carries a bound *app connection's* auth, not a Zapier platform JWT. So it is not the URL external services (Notion DB automations, Luma, Linear, …) should POST to, **and not the route for one Zap to trigger another** — for that, POST to the target's catch URL below, which is unauthenticated by design.
  - The **external catch URL** is `https://hooks.zapier.com/hooks/catch/…` — retrieve it with `get-workflow <workflow-id>` at `.data.triggers[0].details.webhook_url` (only present after a version with the trigger has been published). If `details` is null but the trigger params carry `_zap_static_hook_code`, the URL is `https://hooks.zapier.com/hooks/catch/<account-id>/<code>/` (account id `20495893`). Record it in `zap.json` as `trigger.webhook_url` and use it everywhere an external system is wired up (cutover steps, READMEs, PR checklists).
- **A webhook-triggered durable must SKIP on an empty payload, never throw.** A catch URL is public and gets touched long before it is used properly: pasting it into a Notion **button property** or **database automation**, hitting "test", opening it in a browser, or curling it to check it is live all deliver an empty body (`{"querystring":{}}`). This happens *every* time the Notion side is configured, so a durable that throws turns routine setup into Zapier error alerts for events that never existed — noise that trains everyone to ignore the alerts that matter. Guard at the top of the workflow body, before any id extraction: `if (isEmptyPing(payload)) return { skipped: "empty-payload" };`
  - **Keep the boundary sharp.** *Empty* means no keys, or only known wrapper keys (`querystring`, `headers`, `params`, `body`, `query`) whose values are empty — that skips. A payload carrying **content but no usable id still throws, loudly**: that is a real event whose shape we failed to understand, and silencing it hides the bug. A wrapper key with something in it counts as content. Skipping too broadly is how [`gcal-event-updated-to-meeting-note`](gcal-event-updated-to-meeting-note/)'s predecessor sat dead for three months with no error and no alert.
  - "Skip" means *don't raise*, not *don't log* — log a line so the run history still shows the ping was seen. Reference implementation: `isEmptyPing` in [`xero-contact-from-notion-deal/workflow.ts`](xero-contact-from-notion-deal/workflow.ts).
- **Load the `zapier-sdk` skill before writing or running any Zapier SDK code.** Do it first, not after something fails — it documents the things the CLI won't warn you about (parameter names without suffixes, single-consumption paginated results, `sdk.fetch`/`curl` bypassing org governance, `ZAPIER_CREDENTIALS_*` env var names that fail silently when wrong). Working from memory instead is how a session burns turns on avoidable errors.
  - **The skills are vendored in this repo and invocable as `/zapier-sdk`, `/workflows-modify`, and so on.** `npx skills add` installs them to `.agents/skills/` (the cross-agent path, so Cursor and Codex see them too), which **Claude Code does not scan** — it only discovers project skills under `.claude/skills/`. Each one is therefore committed as a relative symlink `.claude/skills/<name>` → `../../.agents/skills/<name>`, and the `link-agent-skills.sh` SessionStart hook re-creates, repairs and prunes those links. Without them `Skill(zapier-sdk)` fails with `Unknown skill` and this rule silently degrades to working from memory — which is exactly what it exists to prevent. **`.agents/skills/` is the source of truth: never edit through the link**, since `npx skills add`/`update` rewrites that directory and `skills-lock.json` wholesale.
  - **It is not enough on its own for Durables.** That skill explicitly defers `defineDurable`, `run-durable` and `publish-workflow-version` specifics to the version-matched `workflows-*` skills, whose method shapes shift release to release. For anything touching a durable, also load `workflows-modify` (edit + republish an existing Zap) or `workflows-create` (new Zap), and run the `workflows-doctor` compatibility gate they both ask for. **Use `workflows-modify` for its fetch/edit and metadata mechanics — but its "direct publish" step ships straight to production and skips this repo's PR review, so on the normal path you merge a PR and let the pipeline publish (see the "Publishing to Zapier" convention above); publish directly only for a deliberate, stated out-of-band hotfix.** Getting this wrong is silent: `defineDurable` takes `(name, async (ctx, rawInput) => …)` in `0.9.1`, and the plausible-looking `(name, options, async (input, ctx) => …)` publishes fine and then fails at run time with `durable.run is not a function`.
- **Never write `new Date` (or `Date.now()`, `Math.random()`, `fetch`, `setTimeout`) in a durable's workflow body — only inside a `ctx.step`.** `@zapier/zapier-durable` monkey-patches those globals at startup and runs the workflow function in GUARDED mode, so a call outside a step throws `DeterminismViolation: Non-deterministic API "…" called in GUARDED mode`. **The `Date` guard is argument-blind:** its Proxy's `construct` trap asserts *before* looking at the arguments, so `new Date(ms)` and `new Date(Date.UTC(y, m, d))` — both perfectly deterministic — fail exactly as hard as a bare `new Date()`. (`Date.UTC` and `Date.parse` are unguarded, since the `get` trap only special-cases `now`, but don't build on that.)
  - **Calendar arithmetic:** integer maths, no `Date` at all. Copy `daysFromCivil` / `isoDateFromEpochMs` / `daysInMonth` from `drive-invoice-to-xero/workflow.ts`. Paying a task for a `ctx.step` just to format a date is absurd.
  - **A genuine clock read:** wrap it, e.g. `await ctx.step("today", async () => isoDateFromEpochMs(Date.now()))`. The value is then fixed for every retry of that run, which is the whole point of the rule.
  - **Nothing catches this before production.** The guard is a runtime component of the durable package — not a lint, not a publish-time check — so `tsc` passes and `publish-workflow-version` succeeds, and the failure only appears when a real payload reaches that line. It cost `drive-invoice-to-xero` 100% of its runs, and `drive-paid-receipts-to-table` shipped the same latent bug. **When testing a new durable with `run-durable`, use a payload that reaches the main path**, not one that returns at an early guard clause — a skip-path test proves nothing about the code after it.
- Zaps are managed via the Zapier SDK CLI or the Zapier MCP connector. **Prefer the CLI wherever possible** — it's faster and more cost-effective; fall back to the MCP connector (`list_workflows`, `get_workflow_version`, publish tools) only when the CLI can't do the job. CLI setup (install, login, experimental flag for Durables) is documented in the root README under "Setting up the Zapier CLI". This CLI-over-MCP preference is about *reads and one-off operations* — **publishing a durable defaults to the merge pipeline** (see the "Publishing to Zapier" convention above), and any direct `publish-workflow-version`, by CLI or MCP, bypasses PR review.
- **Notion connection: always use the work.flowers workspace connection** — `NotionCLIAPI` connection `02b73654-15c8-85c3-b16a-07304d2beb17` (titled `work.flowers | Dennis <dennis@work.flowers>`). This is the connection that has the work.flowers CRM databases (Contacts, Companies, etc.) shared with it. **Never bind the `Knoxx | Dennis #2` connection (`02b95b31-c152-8800-9036-1107e08f70da`) in this repo** — that connection points at the Knoxx Foods *client* Notion workspace and cannot see work.flowers databases (a write against it fails with `Could not find data_source … shared with your integration "Zapier"`). When publishing, always double-check the `notion_wf` connection id matches the deployed value in the Zap's `zap.json`/README rather than picking one from `list-connections` by title.
- **Notion page creation (repo rule 5).** Every `create_database_item` call passes `template_mode: "default"` so the data source's default template is applied. Don't hardcode per-data-source knowledge — instead copy the `createItemWithTemplate` helper from `luma-guest-registered-to-event-attendance/workflow.ts`, which handles the two constraints:
  1. `template_mode: "default"` **throws** on a data source with no default template — message contains `No default template is configured for this data source`. Catch *that error only* and retry the create without the flag. Do the catch **inside** the `ctx.step` so a template miss doesn't spin the durable's step-retry loop. This also means a default template added in Notion later is picked up with no code change.
  2. A template and inline `content` are **mutually exclusive** ("If you select a template, you cannot include content"). When the page needs a body, create first, then append it in a second `write/page_content` call with `content_format: "markdown"`.

  Properties you pass always override the template's defaults, so normal property mapping is unaffected. Current state (2026-07-25): **Contacts has** a default template (blue `user-circle-filled` icon); **Events and Event Attendance do not**. Exception: `contrast-registrations-to-event-attendance` predates the rule and is retired/disabled — leave it as-is rather than editing source that can't be republished without re-enabling the Zap.
- **AI prompts (repo rule 6).** A Zap with an AI step stores its prompt in `<name>-prompt.md` in the Zap's directory. The file carries a short header explaining which step uses it, then a `## Prompt` heading; everything after that heading is the prompt verbatim. The deployed source embeds a copy in a `const <NAME>_PROMPT = \`…\`` template literal with a comment pointing back at the markdown.
  - `node scripts/check-prompts.mjs` verifies every `*-prompt.md` still matches its embedded copy and exits non-zero on drift; `--fix` re-injects from the markdown. **Edit the markdown first, then run `--fix`** — never hand-edit the literal.
  - **A Zap with more than one AI step needs an `<!-- embed: NAME_PROMPT -->` marker** in each markdown, above its `## Prompt` heading, naming the literal it owns. The checker otherwise matches only the FIRST `*_PROMPT` literal in a file, so two prompts would both be compared against the same one and `--fix` would overwrite it from every markdown in turn — silently. A single-prompt directory needs no marker. `drive-invoice-to-xero` is the two-prompt reference.
  - Keep structured-output field definitions (`outputFields`) in the code, not the markdown — the action needs them as JSON — but keep their descriptions consistent with the prompt's wording.
  - Reference example: [`gmail-attachments-to-drive-by-type`](gmail-attachments-to-drive-by-type/).
- **AI steps use AI by Zapier, and default to `standard/auto`.** Use `AICLIAPI` / `write` / `get_completion` on Zapier's built-in credentials (`authentication_id: "0"`, no connection needed) rather than a raw provider app — a provider app bills to that provider's account instead of Zapier tasks.
  - **The tier is the task cost.** `standard/auto` = 1x, `advanced/auto` = 3x, `premium/auto` = 5x tasks per run, plus the same multiplier again per tool call. Those three sentinels are the only valid values; anything else errors with `Unknown tier sentinel`. Zapier's own default is Advanced, chiefly so steps can make tool calls — **don't inherit that default**, because most steps here make none.
  - **Always start at `standard/auto`.** It is Zapier's recommended tier for classification, extraction and short summaries, which covers nearly everything this repo does. Prompt quality drives accuracy far more than tier does: in `gmail-attachments-to-drive-by-type`, Standard matched Advanced on every case including a multi-row statement-history inference, once the prompt had the right context.
  - **If you suspect Standard won't be enough, say so out loud and prove it either way — never silently upgrade.** Flag the doubt to Dennis, name the specific capability you think is missing (tool calls, long-context reasoning over many documents, subtle multi-step inference), then run the Zap's real cases at both tiers and compare *outcomes*, not vibes. Only move up a tier when a test actually fails at Standard, and record what failed.
  - Every Zap with an AI step keeps a table of verified cases in its README, and its `zap.json` carries an `ai_model` block noting the tier and why. Re-run those cases before changing tier.
  - Validate offline with a harness that calls `run-action` directly — classify real records and print the routing decision — rather than by running the durable, so testing never writes to production systems.
- **Prefer Zapier Tables for backend ID mappings and lookups between systems** (e.g. email → Notion page-id). Table read/write ops don't consume Zapier tasks, so they're the cost-effective place to store cross-system key mappings and do lookups — reach for a Table before a task-consuming app action or extra step. In code, read via `TableCLIAPI.search.find_record` and write via `TableCLIAPI.write.create_record` (Zapier Tables need no connection). Production example: `email-contact-page-zap` uses Table `01JYEPSEARXB2Z6BJRCMFGXBC2` as its email→Notion-page-id map.
- **Durables have no Delay After Queue — no built-in serialization, and no airtight lock is buildable from the current primitives.** "Delay by Zapier" is a directive to the classic Zap engine (park the run, release queued runs FIFO), not an app action — it does not exist in the SDK/MCP action catalog (verified 2026-08-18: a catalog search for "Delay" returns only unrelated apps), so a durable cannot call it. Durable runs for separate trigger events execute **concurrently**. What that means in practice:
  - The plain "delay" half is `await ctx.wait(name, seconds)` at top-level workflow scope (never inside a `ctx.step`).
  - **A find-or-create "lock" — against Notion or a Zapier Table — does not close the race.** Neither surface offers unique constraints or an atomic create-if-absent, so two concurrent runs can both find nothing and both create; check-then-write only narrows the window, it never eliminates it. Don't present a Table lock as real mutual exclusion.
  - **Default posture: make writes idempotent and accept rare duplicates.** Upsert-shaped writes keyed on a stable external ID (email, Xero invoice ID, Luma event ID) plus a cleanup sweep (`merge-duplicate-contacts` is the existing backstop) is the right trade for human-paced triggers.
  - **If a workflow genuinely needs FIFO serialization** (bursty webhooks where simultaneous events are likely), the two honest options are: (a) claim-then-verify via a Table — every run writes a claim record unconditionally with its own run id, `ctx.wait`s past the Table's write-to-readability latency (be generous, waits are free; test the latency before trusting it), then all runs read back the claims and deterministically agree on one winner (lowest record id); or (b) a tiny classic Zap as a serializing front door — trigger → Delay After Queue → POST to the durable's catch URL — which borrows the classic engine's real queue and keeps the durable simple (this creates a zap→zap HTTP edge; register it in the map overlay).
- **Keep the interactive workflow map in sync.** [`docs/map.html`](docs/map.html) is a generated atlas of every Zap and the shared assets connecting them. When a Zap is added/removed/re-statused or an asset relationship changes (a Table read/write, a Notion data source, a Drive folder, the one zap→zap HTTP edge), update the curated semantics in [`docs/map-overlay.json`](docs/map-overlay.json) and run `node scripts/build-map.mjs` to regenerate. `node scripts/build-map.mjs --check` is the drift gate — it fails when the repo, the overlay and the map disagree (new asset ids must be registered or explicitly ignored; every zap dir must sit in exactly one cluster).
  - **The map is published, so a merge to `main` is a deploy.** GitHub Pages serves `/docs` from `main` at `https://work-flowers.github.io/zapier-sdk/map.html`, and [work.flowers/zap-map](https://www.work.flowers/zap-map) embeds that URL in an `<iframe>`. Regenerating the map therefore changes a public page — no extra step, but no undo either.
  - **`map.html` must stay a complete, standalone document** — doctype, `<html>`, `<head>`, `<body>`. It is a full-viewport app (`html,body{height:100%}`, `#stage{position:absolute;inset:0}`, `header{position:fixed}`), which only works when it owns the document. **Never embed its markup directly in a host page**: `#stage` then resolves `inset:0` against whatever the host's nearest positioned ancestor is, collapses to a ~28px sliver, and `body{overflow:hidden}` leaks out and kills the host's scrolling. That is exactly how the first Bullet.so publish failed — the JS ran fine and built all 102 nodes; nothing was visible. The iframe is the fix, and it also gives the map its own CSP so the embedded `data:font/woff2` faces load (Bullet's `default-src 'self' https: wss:` blocks them).
