Zap Publishing Pipeline

Merge a PR into main and the affected Zaps republish to Zapier — with exactly one human click in between. Stop publishing Zaps by hand. Like an animal.

TL;DR

Every merged PR is scanned for real source changes to deployed durables. If there are any, a publish job pauses on the production environment until someone approves it, then republishes each affected deployment exactly as it runs today and commits the new current_version_id straight back to main. The repo always matches what's deployed.

context · how the repo is organised

One Directory per Zap

The zapier-sdk repo is the source of truth for the workFlowers Code Zaps in the main work.flowers Zapier workspace. Each Zap lives in its own top-level directory, and the files inside follow one contract — which is exactly what makes merge-triggered publishing possible: the pipeline knows what to ship and what to leave alone purely from which files changed.

workflow.ts
The durable's source, exactly as published on Zapier. This is the file the pipeline watches: change it (or the directory's package.json) and the deployed Zap republishes.
zap.json
A mirror of the deployed state — workflow ID, current_version_id, trigger URL, enabled state, runtime and dependency versions. The pipeline reads it to know what is deployed, and writes the new version id back into it after every publish. It describes deployment; it doesn't cause one.
README.md
What the Zap does, its trigger, and a Mermaid diagram of the flow — for the maintainer, invisible to the pipeline.

stage 2 · scripts/detect-changed-zaps.mjs

What Counts as a Change

There's no path filter on the trigger — filtering is content-aware, inside the run. The detect job pulls the PR's changed files from the GitHub API (correct whether the PR was merged, squashed, or rebased), then classifies each top-level directory. A change warrants a republish only when it's a source file — .ts, package.json, or package-lock.json — inside a durable directory (one with a zap.json). Everything else is reported and left alone.

You change…ResultWhy
some-zap/workflow.ts republishes Deployed durable code changed — that's the whole point.
some-zap/package.json republishes Dependencies are part of what runs on Zapier.
some-zap/README.md nothing Docs don't change what runs. Reported as metadata-only.
some-zap/zap.json nothing It mirrors deployed state; editing the mirror deploys nothing.
scripts/, docs/, .github/, root files nothing Not Zap directories — skipped by the detector.

The job posts the full report as a PR comment and a run Step Summary, and outputs a single boolean, has_changes. If nothing needs republishing, the pipeline ends here — quietly, with no approval request.

stage 3 · the production environment

The Approval Gate

The publish job runs only when has_changes == 'true', and it is bound to the production GitHub Environment. That environment's Required reviewers rule is the gate: the job pauses before its first step, and nothing reaches Zapier until a reviewer clicks approve. You review the detect report on the PR, click once, and walk away.

Worth knowing: the rule is configuration, not code. Without it, the job would publish automatically on merge — the workflow file says so itself, in a box, at the top.

stage 4 · scripts/publish-changed-zaps.mjs --execute

The Publisher

For each affected deployment, the publisher mirrors the workflows-modify "direct publish" path: it fetches the deployed version's metadata, rebuilds the source files from the repo (same file set, fresh contents), and republishes carrying everything forward — dependencies, durable version, connections, app-versions, the enabled state (a disabled Zap is never re-enabled), and the exact trigger-vs-manual start mode. That last one matters most: getting the start mode wrong silently drops a live trigger, so it's read from two independent signals and verified again after publishing.

It refuses — loudly, publishing nothing — when:

  • refuseThe workflow has an open draft in the editor. A direct publish would be rejected anyway, and folding into a draft is a human decision.
  • refuseThe trigger signals disagree — the saved version has a trigger but the live workflow's triggers[] is empty, or vice versa. Reconcile in the editor first.
  • refuseA deployed source file has no counterpart in the repo. It will not publish a different file set than what is live.
  • refuseRequired metadata can't be read back — no deployed source files, no current_version_id, or the publish response returns no new version id.

The script has a plan/execute split: without --execute it prints the full plan and touches nothing, so the same code is a deeper dry run you can run locally.

stage 5 · repo rule 4

The Sync-Back

After each successful publish, the script rewrites only the current_version_id value inside that Zap's zap.json — a surgical one-line regex replace, not a parse-and-re-serialise, so the diff is one line and the rest of the file stays byte-for-byte. The workflow then commits it as github-actions[bot] and pushes straight to main: one commit, no second PR, no second approval.

The commit message carries [skip ci]. Strictly, this pipeline triggers on PR close, not on push — so the sync-back couldn't re-trigger it anyway. The tag is belt-and-braces protection for any future push-triggered workflow.

detection granularity

Three Directory Shapes, One Detector

A Zap directory isn't always one deployment. The detector maps changed files to affected deployments per shape — a shared-file change hits every deployment in the directory; an entry-file change hits only its own.

Single deployment

└─ zap.json # workflow_id

One workflow.ts, one deployed workflow. Edit it → that Zap republishes.

Shared source

luma-event-to-notion/
├─ workflow.ts # shared
└─ zap.json # deployments[] ×2

One file deployed as two workflows (Luma event created + updated). Edit it → both republish.

Entry files + shared module

├─ workflow.slack.ts
├─ workflow.harvest.ts …
├─ sync.ts # shared by all 5
└─ zap.json # deployments[] ×5

Edit workflow.slack.ts → only Slack republishes. Edit sync.ts → all five do.

why this is safe to trust

The Safety Guarantees

A human approves every publish

The production environment's required-reviewer rule pauses the job before anything reaches Zapier. Detection runs first, ungated, so you approve with the report in front of you.

Deployed metadata is fetched, never assumed

Connections, dependencies, app-versions, enabled state, and — critically — the trigger-vs-manual start mode all come from the live deployment, then get verified after publishing.

Ambiguity means refusal

Open draft, disagreeing trigger signals, a file-set mismatch, unreadable metadata: the run fails loudly and ships nothing. It never guesses.

The sync-back is surgical

One value replaced in place, one [skip ci] commit by github-actions[bot]. No reformatting noise, no second PR to babysit.

Repo always matches deployed

Repo rule 4, enforced by the machine: every publish immediately writes the new current_version_id back into zap.json on main.

✓ verified end-to-end

The first real publish through the pipeline was register-zapier-partner-lead — a webhook-trigger durable. The gate paused, the run was approved, the Zap published with its trigger preserved, and the sync-back landed as commit d0405c5 (PR #94).

credentials

How CI Authenticates

CI uses Zapier client credentials (minted with create-client-credentials), stored as the repository secrets ZAPIER_CLIENT_ID / ZAPIER_CLIENT_SECRET and passed to the CLI via --credentials-client-id / --credentials-client-secret. Only the gated publish job ever sees them — the detect job runs with no secrets at all.

To check the credentials without publishing anything, run the Verify Zapier credentials workflow by hand from the Actions tab. It authenticates and lists durable workflows — the same experimental surface publishing uses, read-only — and prints only a count, so workflow metadata stays out of the logs. Run it whenever the secrets are set up or rotated.
